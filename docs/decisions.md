# Decisions

> Locked technical decisions that explain *why the code is the way it is*. If you (human or AI) are about to "fix" something that looks wrong, check here first — it may be intentional. This is not a history of how the code got here; it states what is true now.

## Container runtime

| Decision | Choice | Why |
|---|---|---|
| Container runtime | **Podman** | No daemon, Quadlet for systemd integration. For rootful vs rootless see "Privilege model" below |
| Unit format | **Quadlet** `.container`/`.network`/`.volume` files | Systemd-native, human-readable, generated by the compiler |
| Orchestration | Quadlet in production; Podman Compose export for local dev/inspection | Never Kubernetes |
| Reverse proxy | **Caddy** | Automatic TLS, simple config |
| Caddy backend addressing | Routes address the backend by Podman container name (`<container-name>:<port>`), never `localhost:<port>` | Caddy runs isolated on the `ownbase-internal` network and cannot reach host-loopback ports; `localhost` silently produced dead routes |
| Caddy published ports | `HostPublishPorts: [80, 443]` only when at least one service has a domain configured (`schema.OwnbaseConfig.HasPublicDomain`) | A domain-less Base (the default state of a fresh Base) has nothing for Caddy to route yet; see "Local development" below for how such a Base is reached instead |
| Network/volume service management | `systemctl restart` (not `start`) for `.network`/`.volume` units | These are `Type=oneshot RemainAfterExit=yes` — `start` is a no-op once they've run once, even if the resource was later pruned. `restart` forces recreation. |
| `Environment=` quoting | Values with spaces are double-quoted by the compiler | Systemd splits unquoted values on spaces into separate `KEY=VALUE` pairs |
| Reload trigger | `SIGHUP` to PID 1, not `systemctl daemon-reload` | `daemon-reload` deadlocks when called from inside a systemd service transaction |
| Capabilities | `DropCapability=ALL` on every container; services opt back in via `add_capabilities:` in `ownbase.yaml` | Most restrictive default; exceptions are explicit and code-reviewed |
| Privilege model | Rootful: units in `/etc/containers/systemd`, system `systemctl`. Rootless: `~/.config/containers/systemd` + `systemctl --user`. Detected at runtime; both the core bootstrap and the per-service applier use the same split | The daemon runs as root for host hardening; user-level Quadlet needs a D-Bus session that doesn't exist for root outside a login context |

## Repository and Git

| Decision | Choice | Why |
|---|---|---|
| Authoritative repo | **External** git repo (e.g. GitHub) holding `ownbase.yaml`; the daemon keeps a checkout at `/opt/ownbase/checkout` (see `internal/configsource`) + one bare clone per service under `/opt/ownbase/repos/` | GitHub is the single source of truth; the tracked ref is applied read-only on the Base |
| Config authority | Operators commit on the tracked ref **client-side** with `ownbasectl` (their git creds), then `POST /reconcile`. Agents may `POST /config` to push a validated proposal branch under `ownbase/agent/*` only — never the tracked ref. Branch protection on the forge is the merge gate | The Base cannot rewrite the operator's config **history on the default branch**. A write deploy key on the config repo (not service repos) is accepted so agents can propose without borrowing the owner key; the forge, not OwnBase, enforces that proposals stay off `main` until merged |
| Sync model | Explicit: every mutating `ownbasectl` command triggers `POST /reconcile`, which fetches the config repo and reconciles. A periodic timer backstop runs as a safety net | No post-receive hook, no SIGUSR1, no webhook, no second git host — reconciles happen when the operator asks, deterministically |
| Service source repos | Every service declares an external `repo:` URL; the daemon keeps a `git clone --bare --mirror` under `/opt/ownbase/repos/<service-name>`. Full commit SHAs short-circuit fetch when already local; **branch and tag refs always refetch** on reconcile | A poisoned bare mirror or upstream force-push must not stick. Only immutable full SHAs are safe to skip |
| SSH identity | One ownbase-managed ed25519 key under `/opt/ownbase/ssh` (`GIT_SSH_COMMAND`, restic-backed). Read-only deploy key on service repos; optional **write** on the config repo only for `POST /config` | Survives rebuild; no ambient `/root/.ssh` |
| SSH config file | **Never honored.** `gitssh.Command` uses the single key + known_hosts only. `RejectConfig` deletes `/opt/ownbase/ssh/config` at daemon start. (Reverses an earlier "config takes precedence" choice.) | A restored or planted `config` can Host-alias every fetch while status still shows the correct URL |
| Proposal push | `POST /config` commits as `ownbased@localhost` in a temp clone; pushes only `refs/heads/ownbase/agent/*` with `--force-with-lease`; never the tracked ref; does not auto-reconcile | Named proposals can be updated; lease refuses if someone else moved the tip; merge stays on the forge |
| Branch name rules | Must start with `ownbase/agent/`; refuses `..`, absolute paths, shell metacharacters, and `main`/`master`/tracked ref | Prevents force-push to protected names under another label |
| Vault config pin | `ensureConfigKnown` backfills empty vault pins only; mismatch warns and leaves the vault unchanged. `restore` re-asserts vault → Base before success | Rooted Base can rewrite `config-source.yaml`; vault is the operator's independent pin |
| Repo ownership | Every bare clone is created by the daemon (root) and then chowned to the admin SSH user recorded at install time (`/opt/ownbase/admin-user`, see `internal/fsowner`) | The daemon runs as root, so a repo it creates is unwritable by any other account by default; chowning keeps file ownership consistent with the admin account |

## Schema and compiler

| Decision | Choice | Why |
|---|---|---|
| Config format | YAML (`ownbase.yaml`) | Human-readable |
| Service declaration | `repo:` — a single external git URL, the only valid user service source | Every service builds from a local read-only clone of its external repo; no container registries and no push-to-Base source path |
| No-registry rule | `image:`/`digest:` do not exist on `ServiceDecl` | Enforced at the schema level, not just convention |
| Core packages | Caddy is installed by the installer, configured via the `core:` block, upgraded via `ownbasectl upgrade` — never declared as an `ownbase.yaml` service | Decouples infrastructure lifecycle from user service lifecycle; `core:` configures, never sets versions |
| `repo:` mechanics | `repo: <url>` → daemon creates a local bare clone at `/opt/ownbase/repos/<service-name>` (keyed by service name, collision-free) and builds from it | Declarative external repos, backed up locally like every other repo |
| Update model | `ownbasectl deploy` resolves the requested ref to a concrete commit SHA (client-side, `git ls-remote`) and commits that SHA to the config repo. Branch-named refs never auto-redeploy; there is no server-side branch-tip pinning and no blank-ref auto-resolution. Agents may push full-document proposal branches via `POST /config` (`ownbase/agent/*`); they do not auto-merge or bump `ref:` themselves | Every deploy to the tracked ref is explicit and deterministic — the committed `ref:` is always a concrete SHA |
| `mode:` field | Parsed but has no effect (deprecated no-op); a warning is emitted when present | Removing it outright would break existing files that reject unknown fields |
| Service image build | `localhost/ownbase-<name>:local`, built by the daemon from the repo at `ref:` | No external registry references; deterministic per ref |
| Compiler output | Deterministic, byte-identical for the same input | Golden-testable, diff-readable, no compiler state |
| Health probe | `health_probe.http: /path` → `# HealthProbeHTTP=` provenance comment in the Quadlet unit | One contract reused by dependency-gating and verified restore |
| Data volume | Named Podman volume per service (`ownbase-<name>-data`), or `volumes:` for multi-volume services with per-volume `backup:` scoping | Isolated, persistent; `backup: ["."]` is what opts a volume into the restic snapshot — omitting it excludes the volume |
| Multi-domain services | `ServiceDecl.Domains []string` alongside the older `Domain string`; `EffectiveDomains()` returns their deduplicated union; the compiler emits one Caddy route per effective domain, all pointing at the same container:port | Lets one service serve multiple public hostnames (e.g. a `.com` and a `.org`) without needing multiple service declarations; `Domain` keeps working indefinitely, no forced migration |
| Caddyfile change detection | `reconcile.DiffOptions.CaddyfileSnapshotAvailable` distinguishes "no prior snapshot" (force a reload) from "a snapshot exists and is identical" (skip) | An empty `CurrentCaddyfile` was previously ambiguous between the two, which combined with reading the snapshot *after* `compiler.WriteOutput` had already overwritten it, meant a fresh Base's Caddyfile was silently never pushed to the running Caddy container |
| Service replicas | `ServiceDecl.Replicas *int` — when set (1..64), the compiler emits N indexed containers `ownbase-<svc>-0`…`N-1`, each with its own loopback publish and (by default) per-replica volumes. Absent = today's single unindexed `ownbase-<svc>`. `replicas: 1` is still indexed so the 1→N transition never renames containers or orphans volumes | Concurrency for long-running workers (coding agents, warm caches, kernels) without copy-pasting the service block N times. Framed as concurrency only — never high availability (arch-principles §12). Not a new top-level key: a replica has the same lifecycle as a service, so it stays on `ServiceDecl` (lexicon: everything running is a service) |
| Refused: `worker_pools:` / leasing / affinity / autoscaling in OwnBase | Routing, session affinity, atomic leases, capacity reporting, and `max_replicas` overflow stay in the application (harness) Postgres — not in OwnBase | A lease/affinity table is live state (arch §2/§11: served, not committed; Base is read-only on the config repo; only the compiler writes `runtime/`). Autoscaling changes topology without a user-authored commit (arch §9). A `worker_pools:` block with routing/capacity sub-keys is a general-purpose orchestrator primitive (arch §8 absolute prohibition on Kubernetes-shaped orchestration). OwnBase provides stable indexed replicas, per-replica volumes, health gates, and rolling replacement; the harness decides which replica receives each session |
| Per-replica volumes | `VolumeDecl.PerReplica *bool` defaults **true** when `replicas:` is set; `per_replica: false` opts into one shared volume mounted by all replicas. The `data_path:` shorthand follows the same default. Backup enumerates every replica volume | Silent shared-volume corruption (four writers assuming exclusive state) is worse than 4× storage. Sharing across replicas of the *same* service does not violate arch §13 (that rule is cross-service) |
| Replica image and secrets | All replicas share `localhost/ownbase-<svc>:local` and `/opt/ownbase/secrets/<svc>.yaml.age`. Units emit `# Service=` and `# BuildImage=` provenance only when replicated so non-replicated configs stay byte-identical on upgrade | One build, one secrets file, N containers. Provenance comments are conditional so upgrading OwnBase does not restart every container on every existing Base |
| Replica identity env | When replicated, each container gets `OWNBASE_REPLICA_INDEX` and `OWNBASE_REPLICA_COUNT` | Derived, no user duplication that can drift; the worker knows who it is without calling the status API |
| Multi-upstream Caddy | A public replicated service emits one route per domain with all replica upstreams on `reverse_proxy` | Free load balancing for the replicated-stateless case; internal workers (`internal: true`) are routed by the harness instead |
| Primary container | gendb `DATABASE_URL`, `ownbasectl tunnel`, and pgBackRest target replica 0 (or the unindexed name when not replicated) via `schema.PrimaryContainerName` | One stable address for consumers that need a single host; do not replicate database providers in v1 |

## SSH tunnel bridge (`ownbasectl tunnel`)

| Decision | Choice | Why |
|---|---|---|
| Agent-safe / human-run split | `create --remote` never prompts for anything, ever, under any circumstance; the only interactive command anywhere in `ownbasectl` is `tunnel <name>`, which may prompt for `sudo` exactly once (mkcert's CA install). The confirmations in `create` (replacing a local VM), `delete`, and `db restore --into production` guard destructive local operations only, and each is skipped by `--yes` or a non-TTY stdin | `create` is expected to be run by an AI agent unattended — an agent cannot answer a TTY password prompt. Starting `tunnel` is itself a human's explicit "I am sitting here, ready" signal, so an interactive prompt there is acceptable |
| No-domain Base exposure | A Base with no domain'd service exposes only SSH externally (Caddy publishes no ports, UFW opens no web ports) — this retires the old assumption that a no-domain Base gets direct, unproxied port access | There is nothing for Caddy to route to yet, and the tunnel bridge reaches services directly over SSH, so publishing ports pre-emptively only widens the attack surface for no benefit |
| Local hostname scheme | Each bridged service's real, already-configured domain with `.localhost` appended verbatim, e.g. `domain: myapp.example.com` → `https://myapp.example.com.localhost:8443` | Per RFC 6761 every OS/browser resolves any hostname *ending in* `.localhost` straight to loopback — no DNS, no `/etc/hosts`, works offline, and never changes across a VM restart/IP change, unlike `sslip.io`-style or mDNS naming (both considered and rejected — see the dev-bridge plan for the full list of alternatives and why each was rejected) |
| Certificate scope | One mkcert certificate covering the full, explicit list of `<domain>.localhost` SANs (not a wildcard) | Arbitrary production domains aren't a single-level suffix of anything shared, so `*.<name>.localhost` can't cover them; mkcert supports multiple explicit SANs in one invocation instead |
| Transport | Direct SSH tunnels to each bridged service's loopback port (`internal/tunnel`, reused unmodified), bypassing Caddy entirely | No port is firewalled on the Base — the loopback publish is only reachable via the SSH tunnel itself; works identically for a local VM or a remote server since both use the same `ServerProfile` |
| Bridge scope | Services with both a `port:` and at least one domain configured are bridged. Services marked `internal: true` are also bridged — the tunnel is their *only* access path (no Caddy route is ever emitted). A domain-less service is never bridged, and never gets a loopback publish at all | Domain-based bridging covers both publicly-reachable and intentionally-private services; `internal: true` makes tunnel-only access a first-class configuration option rather than a workaround |
| Tunnel-only (`internal: true`) services | A service with `internal: true`, `domain:`, and `port:` gets a loopback publish and is reachable via `ownbasectl tunnel`, but the compiler emits no Caddy route for it | Enables private admin UIs, dashboards, and internal APIs to be accessed securely over an authenticated SSH tunnel without ever being internet-facing — the operator explicitly opts in rather than accidentally exposing it |
| Tunnel port allocation | `port(service_i, replica_j) = TunnelBasePort + i + j*N` (sorted port'd services, N = count). Keyed by **container name**. Unreplicated and replica 0 keep the historic one-port-per-service slot; extra replicas use higher bands so adding `replicas:` does not renumber neighbors | Decoupling host-side loopback from container `port:`; configs without `replicas:` stay byte-identical; both compiler and `ownbasectl tunnel` agree without coordinating |
| Tunnel + replicas | `ownbasectl tunnel` bridges **replica 0 only** for a replicated service | The tunnel is a developer inspection tool; reaching one worker is almost always enough. Per-replica local hostnames deferred until asked for |
| Local bind port | `127.0.0.1:8443` by default (`--port` to override), never `443` | Avoids a second, independent privileged-port permission requirement on top of the one-time mkcert install |
| Code iteration loop | No code-sync mechanism of any kind — no bind mount, file watcher, or hot-reload. Iterate by pushing a branch to the service's `repo:` on your git host and running `ownbasectl deploy <base> <name> --ref <branch>`, exactly as in production | A second, untracked way to mutate a running Base would break the "the only mutation path is an explicit deploy" invariant (`docs/foundation/reconstruction-model.md`) |

## Secrets

| Decision | Choice | Why |
|---|---|---|
| Encryption | **age-direct** (`filippo.io/age`), not sops | One recipient per Base is sufficient for V1; sops's multi-KMS/editor-integration advantages don't apply and its dependency footprint is much larger. See [ownbase-yaml.md](ownbase-yaml.md), "Secrets". |
| Storage path | `/opt/ownbase/secrets/<service>.yaml.age`, outside git | No chicken-and-egg declaration in `ownbase.yaml`; path is deterministic from the service name |
| Injection | Start-time, scoped per service, never written to disk as plaintext | Secrets never appear in compiler output |
| Backup | `/opt/ownbase/secrets/` and `/opt/ownbase/age/` are both in every restic snapshot | Secrets aren't in git, so restic is their only persistence; key and ciphertext must travel together |

## Databases (`database:`)

| Decision | Choice | Why |
|---|---|---|
| Form | `database: <provider-service>/<dbname>`, never a bare name | A Base can run two Postgres services; nothing should depend on one of them happening to be called `postgres`. Inference here would be a guess about the most destructive thing on the Base |
| Relationship to `requires:` | The provider must appear in both; validation rejects a `database:` without it | They say different things — `requires:` joins the containers to a network and orders startup, `database:` is what gets created — and a database on a provider the service cannot reach is not worth accepting silently |
| Credential delivery | A `DATABASE_URL` written into the consumer's age-encrypted secrets file, injected by the existing `Secret=` path | No new mechanism, and the URL is in neither git nor the unit file. Composing it into `env:` would put a password in the config repo |
| URL host | The provider's container name and port, not a published port | The database is reached container to container and need not be exposed to the host at all |
| Ownership of the value | Declaring `database:` means OwnBase owns that service's `DATABASE_URL` and rewrites it when the provider's password changes | A rotated password has to reach the consumer somehow. A service whose URL should be managed by hand does not declare `database:` |
| Name charset | Plain SQL identifiers only (letters, digits, underscore) | `CREATE DATABASE` cannot bind its name as a parameter, so the name is interpolated; restricting it is what makes that safe, and every name anyone wants already fits |
| When it runs | Before the compile, in the same reconcile slot as generated secrets | A URL written there is picked up by the secrets fingerprint and reaches the container in the same cycle |
| First reconcile | Reports a skip and retries next tick, rather than failing | Creating a database needs the provider running, which on a fresh Base it is not until later in the same cycle. Converging a minute later is better than a reconcile that errors |

## Host hardening

| Decision | Choice | Why |
|---|---|---|
| Binary signing | **minisign** | Single binary, no PKI |
| Firewall | **UFW**, deny-all + allow SSH always, 80/443 only when `install.PassZeroConfig.ExposeWebPorts` is true (at least one service has a domain configured) | Simple, well-supported on Ubuntu; a domain-less Base has nothing for Caddy to route, so opening 80/443 would only widen the attack surface for no benefit — see "Local development" below |
| Auto-updates | `unattended-upgrades` (security-only, daily) | Standard, operator-invisible |
| Intrusion protection | `fail2ban` with an SSH jail | Well-understood, minimal config |
| Minimum OS | Ubuntu 22.04 LTS (24.04 preferred) | LTS only; no provider-specific assumptions |
| Resumability | Every hardening step is idempotent (checks before acting) | Kill mid-install, restart, continue from where it stopped |

## Backups

| Decision | Choice | Why |
|---|---|---|
| Backup tool | **restic** | Encrypts-first, deduplicated, any backend |
| Postgres PITR | pgBackRest (conditional; no-op when not installed), writing to a Podman volume that restic then backs up — pgBackRest is never configured with a remote (S3/etc.) repo directly | Single remote-store config point (`core.backup:`); no separate pgBackRest credentials to manage |
| Cadence | Backup 1h, verify 24h, retention 30 days by default | Configurable via `core.backup.interval`/`verify_interval` |
| Config vs. credentials | Repo URL in `core.backup:` (git-tracked); credentials in `/opt/ownbase/secrets/backup.yaml.age` | Config survives rebuild; credentials use the normal secrets model |
| Restorable flag | Only set **after** a verified restore drill passes | A backup never verified is not restorable by definition |
| Integrity checks | `restic check --read-data-subset=5%` + file-presence + a **real Postgres recovery** when the restore contains a pgBackRest repository | The first two prove the files came back; only the third proves the database does. A repository can restore cleanly and still fail to recover (a gap in the WAL archive, a full backup aged out from under its incrementals), and no file-level check can tell the difference. Replaces an earlier `pg_controldata` check, which parsed a control file and therefore could not |
| Drill isolation | Recovery runs in `podman run --rm` with no network, `listen_addresses=''`, and `archive_mode=off`, against the restic-restored copy of the repository | The drill must be unable to affect production or write to a backup repository, even by accident |
| Opting out | `core.backup.verify_postgres: false` | The recovery costs real CPU and minutes; operators who cannot spare them should have to say so explicitly, since the alternative is that the recovery path goes untested until the day it is needed |
| Append-only mode | `core.backup.append_only: true` skips scheduled `forget --prune`; owner runs `POST /backup/prune` with transient delete-capable creds | A compromised Base that holds delete rights can wipe the off-machine repo. Non-deleting keys on the Base + owner-driven prune keeps ransomware/root from deleting history while retention still runs |
| Prune credentials | Optional body on `POST /backup/prune` merged over the Base secret for one call; never written to disk. Optional vault admin escrow (`AdminAWS*` / `AdminB2*`) | Delete rights stay off the Base; the vault already holds crown-jewel material and is the natural place for the admin copy |
| Restic password rotation | Two-phase `POST /backup/rekey` (add key → finalize swaps Base secret + removes old keys); client updates vault between phases | Restic multi-key makes every intermediate state recoverable; dual-write stays intentional rather than best-effort-only |
| Dual-write drift check | `/status` exposes `backup_repo` + 8-hex `backup_cred_fingerprint`; checkup compares vault escrow | Stale vault password is a silent restore failure until the day it is needed |

## Point-in-time recovery (`ownbasectl db`)

| Decision | Choice | Why |
|---|---|---|
| Where it runs | `podman exec` inside the Postgres container, from the daemon | That is where the pgBackRest client, the stanza config, and the SSH identity live. An earlier version of `internal/backup/pgbackrest.go` assumed a host-installed `pgbackrest` and had no callers |
| WAL archiving | Postgres's own `archive_command`; the daemon never pushes WAL | Archiving is driven by WAL volume and `archive_timeout`. A daemon polling `archive-push` was doing Postgres's job worse (`PGBackRestArchiveWAL`, deleted) |
| Restore source | The repository Podman volume, mounted read-only | The repository is on the same machine; a restore that needs neither the network nor an SSH key is one less thing to fail when it is needed most. Read-only means a restore cannot damage what it restores from |
| Default destination | `--into scratch`: a second Postgres on `127.0.0.1:5433`, left running | A recovery should start by looking at what came back. Defaulting to production would make the destructive path the easy one |
| Scratch lifecycle | Postgres is the container's own process, under a fixed container name | The instance then lives exactly as long as the container, so `podman rm -f` is a complete teardown and a second restore replaces the first. Backgrounding Postgres instead left podman waiting on a process nobody watched, and `podman exec` failed with "container state improper" |
| Target validation | `--to` is checked against the archive range before anything is stopped | A target past the end of the archive fails with `recovery ended before configured recovery target was reached`, which reads like data loss and is not. On a quiet database the newest recoverable point routinely trails `now()` by minutes, so "restore to right now" hits this constantly. The far end is the last segment's *archive* time, so it bounds the window without being a reachable target — which is why `db status` suggests a restore with no `--to` rather than one aimed at it |
| Recovery completion | Poll `pg_is_in_recovery()` with a bound | `pg_ctl -w` and systemd readiness both return once the postmaster accepts connections, which happens while WAL replay is still running |
| After a production restore | Stop dependants first; take a **full backup** immediately after promotion | A client holding a connection through a data-directory swap sees corruption, not an outage. A promotion starts a new timeline that no existing backup is on, so until a full backup exists the database has recovery history but nothing to recover from |
| Archiver health | Surfaced as a failure, not a count, when `last_failed_time` is newer than `last_archived_time` | A failing `archive_command` is invisible from every other angle — queries serve, the container is up, the disk is fine — while the recovery window stops moving. `pg_stat_archiver.failed_count` is the only place it shows |

## Updates and drift

| Decision | Choice | Why |
|---|---|---|
| Source-ref detection | Local git CLI against the service's bare repo for *reading* current state; fetch always runs for non-SHA refs before that | Branches and tags move; the bare mirror is not trusted as final for mutable names |
| Commit-SHA refs | Skipped in drift comparison | A 40-char hex ref is already maximally pinned |
| Moving a ref | `ownbasectl deploy` only — resolves the ref to a SHA client-side and commits it. There is no autonomous in-place ref mutation | Explicit-only: the daemon never changes what's running on its own initiative |

## Service API access (`ownbase_access`)

| Decision | Choice | Why |
|---|---|---|
| Socket-as-credential | Per-service unix socket; whoever connects is that service principal; no Bearer on the socket path | Filesystem ACL + "only declared services get a socket"; no token distribution into containers |
| Default-deny scopes | `authz.RouteAccess` maps method+path → scope; unmapped = owner-only; `*` still cannot call owner-only routes | Least privilege; new routes stay closed until deliberately mapped |
| Directory bind, not file bind | Host `/run/ownbase/svc/<svc>/` → container `/run/ownbase/`; socket at `api.sock` inside | File binds go stale when the socket inode is replaced on daemon restart |
| Socket mode `0666` | World-connectable socket file; dir `0755` | Containers often run non-root; identity is which socket, not uid |
| Create before apply | `prepareAccess` runs after parse, before container apply; skipped on `--dry-run` | Bind source must exist on first deploy; dry-run must not open/close live listeners |
| `HostPath` mounts | OwnBase-generated only (API sockets); never user-declarable from yaml | Users must not bind arbitrary host paths into services |

## Explain (status)

| Decision | Choice | Why |
|---|---|---|
| Status API | TCP loopback with bearer owner auth, **and** per-service unix sockets when `ownbase_access` is set (same mux) | Daemon already runs as one process; loopback TCP stays off the network |
| Operating guide | A static README.md seeded into the config repo at bootstrap (replaces the auto-init stub; never overwrites user edits). There is no generated `OWNBASE.md` — that mechanism was tried and removed | The repo holds *intent*; observed state (running/healthy, CVE counts) belongs to the status API, not to git — committing it would bury the user's history in noise commits |
| Status contract version | `schema_version` field (currently v3) guards against breaking changes | Consumers check the version before parsing |

## Integration contract

| Decision | Choice | Why |
|---|---|---|
| Build interface | `Dockerfile` at the repo root (or `dockerfile:`/`context:` in `ownbase.yaml`) | No separate manifest needed |
| Routing | All public traffic routes to the declared `port:` | Simplest model |
| Capability network | The service's key in `ownbase.yaml` is also the capability name and the network name (`ownbase-<name>-net`) | Consumers depend on the capability, not the implementation |

## Action taxonomy and audit

| Decision | Choice | Why |
|---|---|---|
| Action model | Closed enum (`ActionType` in `internal/schema/taxonomy.go`), enforced by `NewAction` | An action type that isn't in the taxonomy cannot execute; the audit log is exhaustive |
| Default tiers | Taxonomy still assigns autonomous / notify / approve. Service principals: `TierApprove` is refused; notify actions (e.g. `config.write`, `config.source`) run and are audited. Owner path has no external approval device yet | Tiers already constrain agents; owner-side approve remains additive later — see [foundation/architecture-principles.md](foundation/architecture-principles.md), principle 14 |
| Audit log format | Newline-delimited JSON, `0600` | Appendable, grep-able, not group-readable |

## Remote access (`ownbasectl`)

| Decision | Choice | Why |
|---|---|---|
| Client config | A **KDBX 4 vault** at a path the user chooses, recorded in the non-secret pointer file `~/.ownbase/vault`. There is no `~/.ownbase/config` — `internal/serverconfig` is deleted, with no migration | A plain YAML file holding API tokens was readable by every process running as the user, which is every dependency of every project they open. See "Credential vault and agent" below |
| Transport | `golang.org/x/crypto/ssh` (no `ssh` binary exec) | Pure-Go, no PATH dependency, identical behavior across platforms |
| Host key verification | `~/.ownbase/known_hosts`, trust-on-first-use | Same UX as the `ssh` CLI |
| Token bootstrap | `install.sh` generates a token, writes it to `/opt/ownbase/api-token` (root, `0600`), prints it once; `ownbasectl` fetches it over SSH automatically when adopting an existing Base | SSH is the root credential; the API token only scopes access within the tunnel it opens |
| Token hot-swap | `POST /token/reset` updates the daemon's in-memory token immediately | No daemon restart needed |
| Config mutation | Operator path: `ownbasectl` mutates via `configrepo.go` (clone, edit, push tracked ref, `POST /reconcile`). Agent path: `POST /config` validates YAML, commits as `ownbased`, pushes `ownbase/agent/*` only (`internal/configsource.PushBranch`). Merge on the forge, then reconcile | Two paths, one source of truth. Agents never push the protected ref; operators keep the direct path for low-friction deploys |
| Agent-first CLI | Every `config`/`service` subcommand is a single non-interactive invocation — no editor, no prompts, `--json` for structured output, non-zero exit on validation or transport failure | An AI agent must be able to drive the whole config lifecycle unattended |
| Secrets over the wire | Client sends plaintext over the SSH tunnel only; the daemon re-encrypts and writes to disk; no git commit | The age private key never leaves the Base; plaintext only exists in-memory for the duration of the request |
| CLI distribution | `ownbasectl` is a standalone binary (GoReleaser: darwin/linux × amd64/arm64), with `install.sh` embedded via `go:embed` so a released binary needs no checkout | `ownbasectl create` is the only supported install path — there is no `curl \| bash` |
| Daemon version pinning | Release builds of `ownbasectl` set `OWNBASE_VERSION` to their own version so `install.sh` downloads the matching signed daemon | `ownbasectl` and the daemon stay in lockstep for released installs |

## Provisioning a Base (`keygen`, `create`)

| Decision | Choice | Why |
|---|---|---|
| Owner key generation | `ownbasectl keygen <name>` generates a per-Base ed25519 key **into the vault**, idempotently (an existing key is printed and never regenerated). It is never written to `~/.ssh` | A provider authorizes a key when the machine is created, so the key must exist before `create` can run — it cannot be folded into `create`. Per-Base keys mean retiring a Base revokes exactly one credential, and clobbering an owner key would lock the operator out of their own machine |
| Owner key resolution | The vault, via the agent. An explicit `--ssh-key` still reads a file, for a key the user manages themselves. The public half is **derived from the private key**, never read from a `.pub` file | Two independent lookups previously meant `create` could connect with one key and install a different one into `authorized_keys` — a silent mismatch that only shows up as a lockout later. Deriving it means the two cannot disagree |
| Missing owner key | `create` resolves the key before provisioning. On the local VM path a missing key is generated; on `--remote` it is a preflight failure pointing at `keygen`. An explicit `--ssh-key` that does not exist always fails | A local VM is configured by `create` itself, so nothing needs a key to pre-exist — and without this, a machine with no SSH key at all provisioned a VM that no tunnel could reach, surfacing as a `--wait` timeout long after the install "succeeded". A remote key must be authorized by the provider before boot, so generating one at this point would only produce a key the server has never heard of |
| Preflight | Before uploading anything: retry the SSH dial (`--wait-for-ssh`, default 5m), then check passwordless sudo, Ubuntu version, architecture, RAM, and disk. An SSH auth failure short-circuits the retry loop | A cloud server refuses SSH for up to two minutes after the console says "running", so the first attempt loses a race; and discovering an unfit machine partway through the installer leaves a half-configured box. Waiting cannot fix a rejected key, so retrying one is only a slower error |
| Readiness signal | `--wait` polls `/health` through the tunnel. No daemon change was needed | `install.PassZero` runs before the API mux binds, so the daemon answering *at all* already means hardening finished |
| Profile overwrite | `create` refuses a same-name profile that belongs to a different machine without `--replace`: a different host on the remote path, and on the VM path anything the profile's own `local_vm` marker does not confirm is a local VM. A same-named Multipass VM only settles the case for a legacy profile written before that marker existed; `restore` bypasses the guard internally | Overwriting discards the old server's API token, orphaning a machine that is still running and still billed. The marker decides rather than the VM because a same-named VM can sit next to a remote profile by coincidence — the collision `LocalVM`'s tri-state exists to guard. Restore is exempt because moving a Base to a new host is its entire purpose |
| Host identity | Two hosts count as the same machine when their addresses match literally, normalized for case, whitespace, IPv6 brackets, a trailing FQDN dot, and equivalent IP literal forms. DNS is **not** resolved | Resolving says where a name points now, not which machine the profile was written for: after a rebuild-and-repoint, the stored hostname resolves to the new server, so the guard would approve discarding the old one's token — the orphaning it exists to prevent. A false refusal costs one `--replace`; a false match costs a running, billed, unreachable server |
| Exit codes | `2` usage, `3` preflight, `4` install, `5` not ready in time, `6` refused as destructive, `1` unclassified | An unattended caller needs to tell "you asked for something impossible" from "the box was unreachable" from "the install broke" — the recovery differs for each. `6` is separate from `2` because a safety refusal is not a malformed command: argv is correct, so there is nothing to fix and retry, and the caller must instead choose between `--replace` and a different name |
| SSH port propagation | `--ssh-port` is forwarded to the installer as `OWNBASE_SSH_PORT` | Otherwise the profile records the real port while UFW opens 22 and fail2ban jails 22, leaving the actual SSH port unhardened and flagged as an unexpected listener |

## Credential vault and agent

| Decision | Choice | Why |
|---|---|---|
| Format | **KDBX 4** (KeePass), via `github.com/tobischo/gokeepasslib/v3` | The escape hatch has to be a format, not a promise. KeePassXC and every other KeePass client opens the file with the master password, reads the hosts and tokens, and exports the keys — so nothing here depends on OwnBase continuing to exist. A bespoke encrypted blob would have made the user's own credentials hostage to our code, which is the opposite of the point |
| Location | The user picks it; `~/.ownbase/vault` records the path and holds nothing secret. A path with no extension is treated as a directory and `ownbase.kdbx` is appended | Putting it in a synced folder (iCloud, Dropbox) is the intended case, not a workaround: the provider only ever holds ciphertext, and a second copy is what survives this machine dying. Hardcoding a location would have meant the one file that cannot be regenerated lives wherever we chose |
| What it holds | One entry per Base (host, SSH user/port, API token, config repo URL/ref) and one ed25519 private key per Base | These are the same fields the old `ServerProfile` had. Keeping keys in the same file as the profiles means one thing to back up and one password to remember |
| KDF parameters | Argon2id, 64 MiB, 8 iterations, on vaults OwnBase creates | Matching KeePassXC's defaults rather than the library's much weaker ones. This is the only thing standing between an offline copy of the file and the keys to every machine the user owns, and the cost is paid once per unlock |
| Re-seeding on save | Every save re-randomizes the master seed, encryption IV, KDF salt, transform seed, and inner-stream key | KDBX4 uses ChaCha20. Saving twice under the same key and nonce would reuse a keystream, which is a break, not a weakness — and "save the same vault twice" is the single most ordinary thing this code does |
| Merge on save | The file's mtime and size are checked; if it changed on disk it is re-decoded and the in-memory change is applied on top | The vault is expected to be in a synced folder and openable in KeePassXC. Writing our in-memory copy wholesale would silently discard the entry the user just added by hand — or the one another machine synced in |
| Agent | A resident process (`ownbasectl agent run`) holding the decrypted vault in memory, on a `0600` unix socket at `~/.ownbase/agent.sock`, auto-started on demand and auto-locking after an idle timeout | The alternative is a master-password prompt on every command, which no agent can answer and no human tolerates. This is `ssh-agent`'s model because `ssh-agent` got it right |
| SSH keys | Served over the **standard ssh-agent protocol** on a second socket, with the vault's keys loaded | The existing `tunnel.buildAuthMethods` `SSH_AUTH_SOCK` path then works unchanged, and a private key never reaches disk or leaves the agent. It also means a coding agent can reach a Base without ever being handed a key — it asks for a signature instead |
| Locked-vault error | Its own exit code (`7`), with a message naming `ownbasectl vault unlock` | An unattended caller has to tell "unlock the vault" from "the machine is unreachable"; the fix is entirely different and only one of them is the user's to make |
| Password input | Prompted on a TTY, or read from stdin with `--password-stdin`. Never argv | Argv is readable by any process on the machine through `ps` for as long as the command runs |

## Audited SSH (`ownbasectl ssh`)

| Decision | Choice | Why |
|---|---|---|
| Why it exists | `ownbasectl ssh <base> [-- cmd]` is the sanctioned way to reach a Base shell; AGENTS.md and operating.md direct agents to it and away from raw `ssh` | An agent with root on a machine is exactly as trustworthy as your ability to see what it did. A Base's own logs say what the machine noticed; a recording says what was actually typed and what came back, including the commands that left no other trace |
| Format | **asciicast v2** — line-delimited JSON, one header object then one array per chunk | `asciinema play` renders it with no OwnBase installed, and the desktop app replays it with asciinema's own player rather than a renderer of ours. A proprietary transcript would have made the audit trail depend on us, which defeats having one |
| Input is recorded | Both directions: `"o"` for output, `"i"` for input | Output alone cannot show a command that produced none, and those are the ones worth auditing |
| Not optional | There is no flag to disable recording | A switch would be found and used, and an audit trail with holes in it answers no question |
| Metadata | A sidecar `.json` beside each recording, written when the session **starts** and again when it ends | Listing a thousand sessions must not mean parsing a thousand transcripts, and a session killed mid-flight still has to appear in the trail — those are the interesting ones |
| Who opened it | `$OWNBASE_INVOKER` is recorded as a label; the desktop app sets `app`, an agent sets its own name, the default is `cli` | A shell an agent opened should be distinguishable from one a human opened. It is a label for the trail, not a permission — the recording happens either way |
| Permissions | Recordings, sidecars, and the sessions directory are all `0600`/`0700` | A session can contain anything typed at a prompt, including a pasted secret |
| Recording ids | Sortable UTC timestamp plus a random suffix from `crypto/rand` | The timestamp makes the directory readable and "newest first" cheap. The suffix has to be random rather than clock-derived: the nanosecond field is only as fine as the platform's timer, and the recording is created `O_EXCL`, so a collision does not merely confuse the list — it fails the shell |

## Desktop app (`desktop/`)

| Decision | Choice | Why |
|---|---|---|
| Shape | Tauri 2 + React, where the Rust side does one thing: spawn the bundled `ownbasectl` as a **sidecar** and forward its bytes. Every screen is a rendering of `--json` output | `ownbasectl` already owns the semantics — the vault, the agent, the git commits, the reconcile. An app that reimplemented any of it would be a second control plane that could disagree with the CLI, and then "what is deployed" would have two answers |
| Desired-state changes need a confirmed diff | The app may commit to the config repo (`deploy`, `backup setup`), but never without a dry-run preview of the YAML diff and commit message, and never without an explicit confirm. Host actions (patch, reboot, scanner install, self-update) do not touch git | The commit is one the user asked for by clicking; git remains the source of truth and every change is revertible. A silent commit would still be wrong — hence the mandatory preview |
| Findings | `checkup --json` returns the CLI's findings alongside the raw status, each with a typed `action` (`run` / `open` / `form` / `manual`). The app switches on the kind and never recomputes the verdict | Deciding what counts as a problem — and how to address it — is the CLI's job. A second opinion in TypeScript would drift, and then the app and the terminal would disagree about whether a Base is healthy |
| Self-update | `ownbasectl self-update` → download signed `ownbased` from `releases.ownbase.ai`, minisign-verify, atomic rename, exit so systemd `Restart=always` boots the new binary. Daemon reports `version` on `/status` and `/version` | The Caddy pin lives in the daemon binary (`core.Current`). Image CVEs in core packages are fixed by a newer OwnBase, not by re-pulling the same pin |
| One call per Base | The detail view fetches `checkup --json` once; the security, updates, and backup tabs are sections of that one document | `security`, `updates`, and `backup status` are each that same document with a section picked out, and every one of them costs a fresh SSH tunnel |
| Sidecar allowlist | `desktop/src-tauri/src/cli.rs` names the subcommands the webview may run. `ssh` and `tunnel` are deliberately absent | The webview renders things that came off a Base — transcripts, service names, daemon output. If any of that ever managed to execute script, an unrestricted bridge would run arbitrary commands as the user on every machine they own. `ssh` takes an arbitrary command, which is the exact shape this list exists to exclude: the app reads *recordings* of sessions, it does not open them |
| Sidecar resolution | `.sidecar("ownbasectl")` — the basename, not the `externalBin` path | Tauri resolves a sidecar as `<dir of the running executable>/<name>`, and the bundle puts it beside the app binary. Nothing about the build fails when this is wrong; it fails at runtime, on a user's machine |
| Bundling the CLI | The app ships `ownbasectl` rather than requiring a separate install | The app is useless without it, and bundling pins the two together — the app can never read output from a CLI that predates a field it wants |

## Vulnerability scanning

| Decision | Choice | Why |
|---|---|---|
| Scanner | **trivy** | Single binary, no daemon, scans both OS packages and container images, structured JSON, degrades gracefully when absent |
| Scan scope | Host OS packages + every running container image (discovered via `podman ps`) | Unbuilt images simply don't appear yet — no false "scan failed" noise |
| Cadence | 24h ticker, 5-minute initial delay after daemon start | Long enough not to hammer the trivy DB; delay lets the first reconcile finish building images |
| Remediation | `ownbasectl security fix` → `apt-get upgrade --with-new-pkgs` + `autoremove` on the Base (host packages; plain `upgrade` keeps kernel metapackages back); `ownbasectl upgrade --apply` → rebuild hardened Caddy from the Dockerfile embedded in the daemon + restart. Both trigger an automatic rescan | Caddy is built on the Base (Go 1.26.5 + alpine apk upgrade), not pulled by digest — that is how alpine and stdlib fixes land without waiting on docker-library |
| Findings are only the fixable ones | A host/image CVE finding fires only when `fixable_critical + fixable_high > 0`. Unfixed CVEs (no published patch) are a reading on the Security tab, never a to-do | The number attached to the button must be the number the button changes. Counting unfixed CVEs trained operators to ignore the panel — `security fix` correctly does nothing and the scary number does not move |
| Reboot required | `/var/run/reboot-required` is probed on the secwatch tick and surfaces as `security.reboot_required`. `ownbasectl security reboot` schedules `shutdown -r +1` | After a kernel upgrade, trivy reports the *installed* package clean while the machine still runs the old one. Without the marker the report is wrong in the unsafe direction. The one-minute delay lets `---OK---` leave the box before the tunnel dies |
| Banned IPs are not findings | fail2ban bans render on the Security tab; they do not raise a checkup finding | A ban list is fail2ban working, not a to-do. Raising it on every internet-facing box trains the user to ignore the panel |

## Security monitoring (exposure + access)

| Decision | Choice | Why |
|---|---|---|
| Exposure scan | Local-only: `ss -tlnpH` + `ufw status` + the expected-allowlist derived from `ownbase.yaml` (SSH port, 80, 443) | Deterministic, no cloud dependency, no packets sent; answers "what does this machine believe is reachable" — an off-box scan is a possible future addition, not a requirement |
| Access monitor | `fail2ban-client status sshd` + `journalctl -u ssh` (24h window) | fail2ban and journald are already present; no new daemon, no external blocklist |
| Exposure scan cadence | At most once every 5 minutes | `ss`/`ufw`/`fail2ban-client`/`journalctl` are shell-outs; no need to re-run on every push-triggered reconcile |
| Graceful degradation | Missing tools (`ss`, `ufw`, etc.) return `Available=false` + zero values, never an error | Keeps status queries working on machines where a probe tool is temporarily unavailable |
